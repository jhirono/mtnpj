# Phase 3 — UI Design Contract: Filter & Search Fixes

> Visual and interaction contract for the three UI bug fixes in Phase 3.
> Generated by gsd-ui-researcher.

---

## Scope

This spec covers exactly three bugs. No new features.

| # | Issue | Root Cause |
|---|-------|------------|
| 1 | Search is route-name-only | FTS5 index on `routes` table does not cover `area_name`; route search `?q=` only matches route fields, not the parent area name |
| 2 | Tag filter panels show "No tags available" | (a) `availableTags` state in `FilterPanel.tsx` is initialized as `{}` and never populated; (b) category key strings in `tagCategories` map use old names that do not match the new D1 schema |
| 3 | Grade filter UX is confusing | Enabling the checkbox hard-resets range to 5.10a–5.11a, discarding any prior selection; "Reverse" checkbox on sort has inverted semantics for grade |

## Issue 1 — Area Name Search

### Problem (exact)

`buildAreasQuery` in `worker-api/src/db/queries.ts` uses `area_name LIKE ?` which already covers area search. The `AreaSearch` component already fires `fetchAreas` + `fetchRoutes` in parallel and renders both result groups. **Area search already works.**

The actual user complaint is: when a user types "Swan Slab" wanting to see all routes in that area, they must click the area result (the "F" prefixed item) — clicking a route result ("R" prefixed item) shows only that single route. This selection flow is not obvious.

### Required fix

**No API change required.** The fix is purely UX clarification in the dropdown:

1. Replace the single-character prefix icons (`F`, `R`) with descriptive labels.
2. Replace `F` prefix with a folder icon (existing SVG or the text "Area").
3. Replace `R` prefix with the text "Route".
4. Add hint text below the search input when no area is selected.

### Interaction spec

**Dropdown structure (unchanged layout, updated labels):**

```
[ Search results - click to select ]
  Areas
    [folder] Swan Slab / Yosemite Valley / ...    [Select]
  Routes
    [route] Munginella  5.6                       
            Swan Slab / Yosemite Valley
```

- "Area" rows: selecting loads all routes in that area and its sub-areas (existing behavior, `handleAreaSelect`). Label the action indicator as "Select" (currently "+" / "V").
- "Route" rows: selecting shows that single route in detail view (existing behavior). No label change needed — the grade and area path sub-line already provide context.

**Hint text below input when no area is active:**

```
Search by area name to see all routes in that area,
or search by route name to find a specific route.
```

Render as `text-xs text-gray-500` below the input. Hide once an area is selected.

**Selected area chip:** Keep existing design. No change.

## Issue 2 — Tag Filter Category Mapping

### Problem (exact)

**Bug A:** `FilterPanel.tsx` line 17: `const [availableTags] = useState<Record<string, Set<string>>>({})` — this state is never populated from the API. There is no `useEffect` that fetches available tags. The `tagCategories` `useMemo` filters every tag through `availableTags["X"]?.has(tag)` which always returns `false` because the map is always empty. Result: all tag categories collapse to zero items and are hidden by the `nonEmptyCategories` filter.

**Bug B:** The category key strings used in `tagCategories` do not match what Phase 3 stores in `route_tags` (a JSON column in D1). Old keys used in UI vs. new canonical keys from `03-CONTEXT.md` D-16/D-19:

| UI key (old, broken) | D1 key (new, canonical) |
|----------------------|------------------------|
| `"Route Style & Angle"` | `"Route Style"` |
| `"Hold & Movement Type"` | `"Movement"` |
| `"Crack Climbing"` | `"Crack Climbing"` (unchanged) |
| `"Rope Length"` | `"Logistics"` |
| `"Weather & Conditions"` | removed (no replacement) |
| `"Approach & Accessibility"` | removed (no replacement) |
| `"Crowds & Popularity"` | removed (`low_crowds` dropped in D-18) |
| `"Difficulty & Safety"` | split: `"Safety"` + `"Quality"` |
| `n/a` | `"Logistics"` (new — pitch, rope, anchors) |
| `n/a` | `"Safety"` (new) |
| `n/a` | `"Quality"` (new — `classic_route` only) |

### Required fix

**Fix A:** Remove `availableTags` gating entirely. The tags that can appear in each category are known at build time from `03-CONTEXT.md`. Render all tags statically; let the filter operate on the `route_tags` JSON returned from the API. If a tag appears in zero routes the filter will still show it but produce zero results — acceptable for a fix-only scope.

**Fix B:** Replace the entire `tagCategories` definition with the new 6-category structure. Update all `toggleTag` / `isTagSelected` call sites to use the new category key strings. Update the tag filter logic in `App.tsx` `filteredRoutes` useMemo to match the new category keys.

### Tag filter logic in App.tsx

The `filteredRoutes` useMemo currently has special-case logic for `"Difficulty & Safety"` with `exclude_sandbag` and `exclude_runout_dangerous`. These tags no longer exist in the new schema. Replace with straightforward inclusion logic:

```typescript
return currentFilters.tags.every(({ category, selectedTags }) => {
  const routeTagsForCategory: string[] = parsedTags[category] || [];
  return selectedTags.some(tag => routeTagsForCategory.includes(tag));
});
```

Multiple selected tags within a category are OR-logic (match any). Multiple categories selected are AND-logic (must satisfy all categories). This matches existing behavior for the non-exclusion path.

## Issue 3 — Grade Filter

### Problem (exact)

1. **Hard-reset on enable:** Enabling the grade filter checkbox always sets `{ min: "5.10a", max: "5.11a" }` regardless of what the user may have selected before disabling. If a user disables and re-enables, their selection is lost.
2. **Max-grade onChange logic is inverted:** In the max-grade `<select>` onChange handler, when `max` moves below `min`, it sets `min: e.target.value` (correct: clamp min up to match max). But the condition `GRADE_ORDER.indexOf(e.target.value) >= GRADE_ORDER.indexOf(filters.grades.min)` returns `filters.grades.min` unchanged when the new max is >= min. This is correct logic. The grade filter does function, but the hard-reset UX causes user confusion.
3. **Default state:** When filter is disabled, `grades: { min: "", max: "" }` bypasses API filtering entirely (correct). When enabled, the locked default 5.10a–5.11a is sent to the API.

### Required fix

1. **Persist selection on toggle:** Store the last-used grade range in a ref. On re-enable, restore from ref instead of hard-setting 5.10a–5.11a. If no previous range, default to `{ min: "5.10a", max: "5.13d" }` (wider default is more useful).
2. **Remove the "no grades" empty state:** When grade filter is disabled, show a single line: "Grade filter off — showing all grades". When enabled, show the two dropdowns. No other changes.
3. **Sort "Reverse" label:** The sort control's "Reverse" checkbox has semantics that differ per sort option (for grade, unchecked = easiest first; for votes, unchecked = most votes first). This is confusing but out of scope for this fix. Add a `title` attribute to the checkbox: `title="Ascending order"` — minimal change, no layout impact.

## Mobile Considerations

The layout is `flex-col` on mobile and `md:flex-row` on desktop. The filter panel is full-width on mobile, appearing above the route list.

**Current problem on mobile:** The filter panel (`md:w-72`) is `sticky top-4` inside a div, which has no effect on mobile flex-col layout — it scrolls with the page. The filter panel can be very tall (6 tag categories + grade + type + sort), making it hard to reach routes.

**Required fix (minimal):** Add a collapsible wrapper around the filter panel on mobile only. Implementation:

- Add a "Filters" toggle button visible only on mobile (`md:hidden`) above the filter panel.
- When collapsed (default on mobile), hide `FilterPanel` and show only `AreaSearch`.
- When expanded, show both `AreaSearch` and `FilterPanel`.
- Button label: "Show Filters" / "Hide Filters".
- Use Tailwind `hidden` / `block` classes toggled by a boolean state in `App.tsx`.
- Desktop behavior unchanged (`md:block` always shows the panel).

**Touch targets:** All clickable filter category buttons must have at least 44px height on mobile. Current `py-1.5` gives ~36px. Add `py-3 md:py-1.5` to category toggle buttons inside `FilterPanel`.
